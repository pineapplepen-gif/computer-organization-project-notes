边缘设备实验方案

在边缘设备上的实验将采用学校发的边缘大模型设备，也就是 NVIDIA Jetson Orin Nano Super，设备内存有8 GB，配备了电线和各种插件，相关资料请参考Jetson Orin Nano Super 8B 使用指南

本实验需要测量的指标有：

  • 边缘平台可达带宽、FP16 GEMM 算力、功耗和热状态；
  • 降配 UNet 的 Baseline/Treatment FLOPs、访存下界、算术强度和 Roofline 区域；
  • FFN 压缩引起的算术强度变化方向；
  • 整板功耗代理下的 FLOP/J 和 Byte/J 趋势。

E3：边缘平台参数标定

6.1 标定口径

Roofline 使用两个参数：

[
I^*{\text{edge}}=\frac{\pi{\text{measured}}}{\beta_{\text{measured}}}
]

其中：

  • (\pi_{\text{measured}})：实测 FP16 GEMM 吞吐，单位 FLOP/s；
  • (\beta_{\text{measured}})：实测可持续内存带宽，单位 Byte/s；
  • (I^*)：屋脊点，单位 FLOP/Byte。

标称值和实测值都要记录。主图用实测算力/带宽画实线，标称值仅作虚线对照。

6.2 实测带宽

目的： 测达到平台可持续 DRAM 带宽，而不是测小数组缓存命中。

建议使用 GPU 端大张量复制或多个足够大的数组，分别测试 256 MiB、512 MiB 和 1 GiB 级别的缓冲区。对小尺寸到较大尺寸绘制曲线，选择吞吐已进入平台的区间。

核心流程：

  1. 分配源、目标 GPU 张量；
  2. 预热至少 3 次；
  3. 用 CUDA Event 而不是 Python 墙钟计时；
  4. 每次计时至少 1 秒，重复 5 次；
  5. 丢弃首次结果，取中位数；
  6. 记录张量大小、dtype、设备、次数和中位数。

对于一次复制：

[
\text{Bytes}=2\cdot N\cdot \text{itemsize}
]

[
\beta_{\text{copy}}=\frac{\text{Bytes}}{t}
]

说明：

  • 读源和写目标都要算入字节；
  • 不能只除一次元素数；
  • CPU 侧拷贝与 GPU 侧拷贝分别记录，不用 CPU 带宽替代 GPU 带宽；
  • 若不同缓冲区大小结果差异很大，选已经进入平台的一段，并在报告中给出曲线。

6.3 实测 FP16 GEMM

已确认设备为 8 GB 统一内存，GEMM 标定首先使用 M=N=K=2048。只有 2048³ 稳定且统一内存余量充足时，才尝试 4096³；不要直接使用 16384³，也不要在运行模型的同时做 GEMM 标定。

流程：

  1. 创建 FP16 输入矩阵；
  2. 预热 5 次；
  3. 运行至少 20 次，保证总计时跨过功耗采样分辨率；
  4. CUDA Event 同步计时；
  5. 根据实际浮点运算量计算吞吐。

[
\text{FLOPs}_{GEMM}=2MNK\cdot R
]

[
\pi{\text{measured}}=\frac{\text{FLOPs}{GEMM}}{t}
]

其中 (R) 是有效重复次数。

记录：

  • 实际 M/N/K；
  • 重复次数；
  • 每次中位耗时；
  • 中位吞吐；
  • 最小/最大值；
  • 是否发生 OOM；
  • 是否发生热降频；
  • 功耗采样区间。

如果 4096³ 能运行但吞吐尚未稳定，可比较 2048/4096，不要为了追求更大矩阵而牺牲可复现性。

7.2 冻结模型

固定：

  • 降配 UNet 代码 commit；
  • 权重文件 SHA-256；
  • 分辨率、帧数、batch；
  • latent 形状；
  • 随机种子；
  • condition 生成方式；
  • 模型是否使用 FP16；
  • 目标 FFN 模块前缀。

Baseline 和 Treatment 必须是同一份代码、同一份输入、同一环境下的两个条件。不能一边跑 FP32、一边跑 TensorRT 量化版本。

7.3 算子兼容性检查

优先走 PyTorch/TensorRT 以外的同一路径，以保持与云端相同的 hook 口径：

unet = unet.half().to("cuda")
unet.eval()
with torch.inference_mode():
    out = unet(x, t, cond)

逐个记录是否出现：

  • not implemented for 'Half'；
  • 3D 卷积回退；
  • attention 的 einsum/baddbmm 回退；
  • CPU fallback；
  • OOM；
  • TensorRT 不支持的算子。

判定规则：

  1. 同一 PyTorch FP16 路径可运行： 可进入定量比较，且与云端方法最一致。
  2. 少量非核心算子回退 CPU： 可保留该方法，但必须记录算子名，并禁止把该运行的墙钟时间当作平台峰值或 Roofline 实测点。
  3. FFN、主要卷积或 attention 大量回退： 当前运行不能代表 GPU 数据通路，转入平台参数标定 + 云端算术强度外推的降级路径。
  4. 必须改为 INT8/低精度才能运行： 另立实验条件，不能直接与 FP16 结果作单变量比较。

E5：内存与输入级别门禁

8.1 阶梯

以下尺寸是课程方案中的候选，不是对实际设备能力的预先承诺：

级别 像素分辨率 帧数 Batch
L0 512×256 14 1
L1 512×256 8 1
L2 384×192 14 1
L3 256×256 8 1

8 GB 统一内存不足以稳妥运行完整 SVD XT 推理管线，因此边缘侧不把完整 SVD 管线作为 Baseline，而使用 W1 门禁确定的降配 UNet。L0 仍需做一次快速尝试，用来记录“容量墙”在哪里发生；L0 OOM 本身就是有效实验现象，不代表实验失败。

若模型代码只接受 latent，必须先根据 VAE 缩放因子和 config 反算 latent 尺寸，不能把像素尺寸直接当作 UNet 输入。

8.2 测试顺序

  1. 从 L0 开始；
  2. 用相同固定输入各跑一次；
  3. 每轮前执行 gc.collect() 和 torch.cuda.empty_cache()；
  4. 记录 max_memory_allocated()、max_memory_reserved() 和运行时错误；
  5. 如果 OOM，记录失败级别和错误文本；
  6. 找到 Baseline 与 Treatment 共同可运行的最高级别；
  7. 在该级别连续运行至少 5 次，确认不是偶然成功。

由于设备只有 8 GB 统一内存，建议把“连续 5 次前向后仍有至少 1 GiB MemAvailable”作为本课程实验的项目安全线，同时记录 max_memory_allocated()、max_memory_reserved() 和 /proc/meminfo。只看到峰值分配未达到 8 GB，不能证明运行安全，因为 CUDA 缓存、桌面和内存碎片仍可能造成后续 OOM。若实验需要关闭图形界面以提高余量，必须将其作为环境差异单独记录，且 Baseline/Treatment 均使用同一状态。

8.3 验收

满足全部条件才锁定：

  • Baseline 和 Treatment 均通过；
  • 连续 5 次无 OOM；
  • 输出形状一致；
  • 无重大 CPU fallback；
  • 运行后温度和功耗仍稳定；
  • 配置常量写入实验配置文件和报告。

如果只有 L0 能跑 Baseline、Treatment 需要降到 L1，则不能跨级比较，统一回退到 L1。

E6：边缘 Baseline 分层测量

9.1 测量顺序

每个变体独立进程运行，避免缓存池和热状态相互污染：

  1. 加载环境；
  2. 固定随机种子；
  3. 创建固定输入；
  4. 2–3 次 warmup；
  5. 5 次正式测量；
  6. 丢弃首次；
  7. 取中位数并保存原始数据。

9.2 FLOPs 与访存下界

以 hook 计算为主口径。至少分为：

  1. 整个 UNet；
  2. FFN；
  3. attention；
  4. 卷积。

权重访存：

[
B_{\text{weight}}=\sum_i \text{numel}(W_i)\cdot 2
]

激活访存下界：

[
B_{\text{act}}=\sum_j
\left[\text{numel}(X_j)+\text{numel}(Y_j)\right]\cdot 2
]

总访存下界：

[
B{\text{L1}}=B{\text{weight}}+B_{\text{act}}
]

[
I=\frac{\text{FLOPs}}{B_{\text{L1}}}
]

报告必须声明：

  • 这是理论下界，不是 FPGA/DRAM 性能计数器；
  • 同一张量被多层引用时，按每层独立计入，是当前口径的一部分；
  • Baseline 和 Treatment 使用同一套 hook；
  • FFN 前缀由 named_modules() 实际打印后确定，不能靠猜测命名。

9.3 时间与功耗分开测

为减少 profiler 对功耗和墙钟的干扰，采用两类运行：

运行 A：结构归因

  • hook 记录 FLOPs、输入输出形状、dtype、device；
  • profiler 只用来交叉检查算子分布；
  • 不使用这一轮的耗时作为最终能效时间。

运行 B：计时和功耗

  • 不开启 profiler；
  • 连续运行 10–20 次前向；
  • 外层用 time.perf_counter() 计总时间；
  • 同步用 tegrastats 记录功耗；
  • 第 (i) 次平均时间为总时间除以有效次数。

E7：Treatment 与单变量控制

10.1 插入 FFN 瓶颈

  1. 用 Baseline 的层级数据确认 FFN 占比；
  2. 记录被替换 Linear 的完整模块名；
  3. 只替换 FFN 内部 Linear，in_features 和 out_features 保持不变；
  4. 设置瓶颈比例 (r=0.5)；
  5. 保存模块列表和替换数量；
  6. 检查注意力投影未被误替换。

10.2 结构验收

替换后检查：

  • 输出形状与 Baseline 一致；
  • 参数更新只发生在预期模块；
  • hook 覆盖的层数与预期一致；
  • 没有自动 dtype 转换或 CPU 回退；
  • 经过相同输入时 forward 不报错；
  • 模型总参数和 FFN 参数变化能被记录。

10.3 重测

对 Treatment 重复 E6 的全部步骤，不改变：

  • 输入；
  • batch；
  • 分辨率；
  • 帧数；
  • dtype；
  • 功耗模式；
  • 冷却策略；
  • hook 统计口径；
  • 测量轮数。

为了控制时漂移，建议顺序执行：

  1. Baseline；
  2. Treatment；
  3. Baseline 复核。

第二次 Baseline 与第一次中位数差异原则上应小于约 5%，或者能够由热/频率变化解释。否则数据不可用于方向比较。

E8：Roofline 与能效分析

11.1 平台定位

对每个层级计算：

[
I{level}=\frac{\text{FLOPs}{level}}{B_{level}}
]

[
q{level}=\frac{I{level}}{I^*}
]

其中：

  • (q<1)：相对该平台为 memory-bound；
  • (q>1)：相对该平台为 compute-bound；
  • (q\approx 1)：接近屋脊点。

同时输出：

  • 用实测 (\pi,\beta) 绘制的屋脊点；
  • 用标称值绘制的虚线屋脊点；
  • Baseline 和 Treatment 点；
  • 箭头方向和变化百分比。

11.2 方向一致性

定义：

[
\Delta I=I{\text{treatment}}-I{\text{baseline}}
]

只比较符号：

  • 同为增加：方向一致；
  • 同为减少：方向一致；
  • 一增一减：方向相反；
  • 变化在测量波动内：判为“不显著”，不要强行判方向。

跨平台不使用绝对 FLOPs 或绝对访存下界作直接数值比较，因为云端与边缘侧的降配模型不是同一个基线。

11.3 能效指标修正

原方案中的

[
\text{FLOPs}/(\text{Bytes}\times P_{avg})
]

更接近“每瓦每字节的计算量”，不是标准的每焦耳计算量。建议改用：

单次前向的能量代理为：

[
E{\text{forward}}=
\frac{P{avg}\cdot t_{\text{loop}}}{N}
]

其中 (N) 是功耗测试循环中的有效前向次数，(t_{\text{loop}}) 是这 (N) 次前向的总时间。若只测一次完整前向，则 (N=1)。

[
\eta{\text{FLOP/J}}=
\frac{\text{FLOPs}}{E{\text{forward}}}
]

[
\eta{\text{Byte/J}}=
\frac{B{\text{L1}}}{E_{\text{forward}}}
]

其中 (P_{avg}) 取稳定负载段的时间加权均值；若采样间隔固定，可同时报告中位数和均值。不要把空载功耗当作前向功耗，也不要把 VDD_IN 说成 GPU 核功耗。

任务卡 T6：屋脊点计算与平台参数锁定

需要准备的材料

需要进行的最小步骤

  1. 将带宽统一为 Byte/s，将 GEMM 吞吐统一为 FLOP/s。
  2. 计算 I* = π_measured / β_measured。
  3. 计算标称屋脊点，并明确标称数据是否有型号依据。

需要的分工成员

  • A：确认型号、模式、冷却和硬件来源。
  • C：独立复算数值和小数位数，检查单位换算。

实验阶段性成功标志

任务卡 T8：算子兼容性与 PyTorch/TensorRT 路径门禁

6. 与课程方案的衔接结论

本次官方底板资料能够支持以下实验设计：

  • 说明边缘节点的存储层次、统一内存、接口和供电约束；
  • 解释为何原尺寸 SVD UNet 在 8 GB 统一内存上可能先遭遇容量墙；
  • 用实测带宽和 GEMM 算力计算边缘屋脊点；
  • 用统一内存整板功耗记录做 VDD_IN 能耗代理；
  • 把 FFN 压缩的影响从“云 GPU 上的单平台结论”扩展成“平台约束下的方向性对照”。

本次官方资料不能直接证明：

  • 具体数据库或模型的端到端延迟；
  • SoC 的真实 FP16 峰值；
  • 设备一定是 Nano Super；
  • TensorRT 转换后仍保持与 PyTorch 理论下界相同的访存口径。

因此，报告中最稳妥的表述是：

边缘侧先进行型号识别、功耗/热门禁和平台参数标定；在降配 UNet 上分别测 Baseline 与 FFN Treatment。通过与云端相同的方法学口径计算分层算术强度，并在边缘实测屋脊点上定位。若边缘模型无法以可接受方式运行，则仅用平台标定和云端算术强度做理论外推，并明确降低证据等级。
