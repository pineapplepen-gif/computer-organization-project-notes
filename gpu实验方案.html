GPU实验方案

0. 实验边界与五人配置

0.1 必须锁定的边界

  1. 云端实验对象是 原尺寸 SVD UNet 的前向，不是完整 SVD 视频生成管线。
  2. 不在云端报告中加入 VAE 解码、视频采样器或端到端视频质量结论。
  3. Baseline 与 Treatment 必须使用同一输入级别、同一 dtype、同一模型代码和同一测量口径。
  4. 云端 Baseline 是原尺寸 SVD UNet；边缘 Baseline 是降配 UNet。两侧只比较变化方向，不直接比较绝对 FLOPs 或算术强度。
  5. Roofline 主图使用云端实测 FP16 吞吐和实测可达带宽；标称值只作虚线对照。
  6. 云端没有可靠的整板/GPU 功耗采集能力，因此 RQ4 不在云端作定量回答。
  7. 输入的 latent shape 必须由 config、VAE 下采样倍率和实际 forward 签名反算。当前文档中的示例 (1,4,14,32,32) 仅是形状示例，不能未经核对直接当成 512×256 输入的最终 shape。

0.2 五名成员

每名成员固定一个主责，同时承担交叉复核任务。

成员 角色 主责 关键交叉义务
A 云平台与资源负责人 GPU 实例、CUDA、驱动、存储、成本、配额、环境生命周期 审核平台参数和资源记录
B 模型集成负责人 SVD 代码、权重、config、模型适配、FFN 定位 审核 Treatment 只修改目标 FFN
C Baseline 测量负责人 原尺寸 UNet Baseline、FLOPs/字节、计时和重复测量 不得单独批准自己的最终 Baseline 数据
D Treatment 与复现负责人 FFN 瓶颈构造、Treatment 测量、A/B/A 复核 负责发现 Baseline 与 Treatment 的非目标差异
E 数据质控与报告负责人 原始日志、CSV/JSON、统计、图件、结果包和结论审计 独立复算关键数字，维护数据字典

0.3 数据职责分离原则

  • C 负责 Baseline，D 负责 Treatment；B 负责模型结构正确性，E 负责数据独立性。
  • 任何人不得直接覆盖原始 run_*.json；修正结果只能新增文件并写明原因。
  • 每个关键结果至少有两名成员看到原始输出：一名执行者、一名复核者。
  • 所有最终主结论必须能追溯到 run ID、代码 commit、模型哈希和平台校准版本。

1. 实验阶段和最小交付

阶段 任务 最小交付 目标
准备 CL0–CL6 项目章程、平台表、环境冻结文件 确认云端平台与模型可运行
Baseline 门禁 CL7–CL11 输入配置、显存阶梯、FFN 门禁表 找到双方可跑的最终配置
测量 CL12–CL18 Baseline/Treatment 原始数据、复核记录 完成云侧对照
分析 CL19–CL20 Roofline CSV、图和结论包 回答 RQ1–RQ3 云侧部分
验收 CL21 可复现数据包和交接单 交给跨平台组

建议使用 4 个实验日：

日期 实验内容 主要负责
第 1 天 CL0–CL6：资源和环境冻结 A 主导，B/E 复核
第 2 天 CL7–CL11：模型加载、显存和算子门禁 B 主导，C/D/E 参与
第 3 天 CL12–CL18：Baseline/Treatment 测量 C、D 主导，A/B/E 复核
第 4 天 CL19–CL21：Roofline、报告和数据包 E 主导，A/B/C/D 参与

2. 可执行任务卡

每张任务卡只规定最小可验收闭环。任务卡通过后才能进入下一张。

任务卡 CL0：冻结项目问题和实验对象

需要准备的材料

  • 课程《计组作业大纲》v5.0、《实验计划》云 GPU 分册。
  • 项目 RQ、数据字典草案、实验命名规则、共享目录。
  • 当前模型仓库、权重来源和 config 的路径记录。

需要进行的最小步骤

  1. 由全组逐条确认 RQ1、RQ2、RQ3 的边界。
  2. 写明云端只测原尺寸 SVD UNet 前向，不测完整生成管线和视频质量。
  3. 约定 run ID：cloud_<baseline|treatment>_<level>_rNN。
  4. 约定原始数据不可覆盖、修正留痕。
  5. 在项目看板上标注交付给跨平台组的字段。

需要的分工成员

  • A：说明云资源与实验周期限制。
  • B：解释 SVD UNet、FFN 和 attention 的模型边界。
  • C：确认 Baseline 测量口径。
  • D：确认 Treatment 及复核方案。
  • E：整理 RQ 与数据字典，检查边界是否自洽。

实验阶段性成功标志

  • 五人对实验对象、输入级别和禁止项没有歧义。
  • run ID、数据目录和交付字段已经冻结。
  • 形成一页《云端对照组实验章程》，五人确认。

任务卡 CL1：申请与验收云 GPU 资源

需要准备的材料

  • 云 GPU 账号、项目配额、SSH 或平台终端、持久化存储。
  • 安全说明、成本预算、镜像/容器仓库、实验目录。

需要进行的最小步骤

  1. 启动已确认实际型号的 GPU 实例，记录实例区域和规格。
  2. 建立共享数据目录和每人只写自己子目录的权限规则。
  3. 检查至少可容纳模型、输入缓存和至少 20 组 run 的磁盘空间。
  4. 确认网络、SSH、进程终止和实例关闭流程。
  5. 禁止把账号密钥、访问令牌和下载凭据提交到代码仓库。

需要的分工成员

  • A：创建实例、分配存储和记录资源开销。
  • B：检查模型安装所需网络和磁盘空间。
  • C：确认能够保存 Baseline 日志。
  • D：确认能够保存 Treatment 和复核日志。
  • E：检查权限、脱敏和备份规则。

实验阶段性成功标志

  • GPU 实例可登录，存储路径可写，磁盘余量满足实验。
  • A、C、D、E 均能在约定路径读写日志，且不能覆盖他人原始数据。
  • 身份凭据没有进入仓库或报告。
  • 资源成本、实例编号和关闭责任人已记录。

任务卡 CL2：记录 GPU 身份和标称参数

需要准备的材料

  • nvidia-smi、PyTorch、GPU 官方规格页或来源记录。
  • platform_inventory.md、平台参数表。

需要进行的最小步骤

  1. 执行 nvidia-smi --query-gpu=name,memory.total,memory.used,compute_cap,clocks.max.sm,clocks.max.mem,power.limit --format=csv。
  2. 记录 CUDA、驱动和 PyTorch 版本。
  3. 记录 GPU 是否处于 MIG、共享实例或受限配额。
  4. 从官方来源填写标称 FP16 算力和带宽。
  5. 同时记录实例实际可用显存，而不只记录硬件总显存。

需要的分工成员

  • A：执行硬件查询并确认 MIG/共享状态。
  • B：确认 CUDA 与 PyTorch 编译环境匹配。
  • C：准备后续 Baseline 测量目录。
  • D：记录测量注意事项和实例限制。
  • E：核对型号、单位、来源和可追溯性。

实验阶段性成功标志

  • 实际 GPU 型号、显存和编译版本已确定。
  • 标称参数有明确来源，不把租户配额写成硬件规格。
  • 若 GPU 为 MIG 或共享切片，已明确后续只用实测参数画主图。

任务卡 CL3：冻结环境镜像和运行命令

需要准备的材料

  • NVIDIA 容器或云实例镜像、锁文件、代码 commit。
  • environment.lock、launch.sh、只读配置目录。

需要进行的最小步骤

  1. 固化镜像 digest 或完整依赖版本。
  2. 为模型代码建立固定 commit，关闭实验期间的自动拉取。
  3. 检查 Python、PyTorch、CUDA、cuDNN、torchvision 版本。
  4. 运行一次 CUDA FP16 矩阵乘自检。
  5. 把启动命令和 GPU 编号写入 launch.sh，确保 Baseline/Treatment 可直接重放。需要的分工成员
  • A：确认镜像与 GPU 驱动兼容。
  • B：建立模型入口和启动脚本。
  • C：检查 Baseline 启动命令不含随机变化项。
  • D：准备 Treatment 启动脚本的唯一差异项。
  • E：保存全部版本和命令哈希。

实验阶段性成功标志

  • 新进程能从冻结命令启动模型。
  • CUDA 可用，FP16 GEMM 可以运行。
  • Baseline 和 Treatment 的启动差异只有模型变体参数。
  • 镜像/依赖清单可重新创建相同环境。

任务卡 CL4：校验代码、权重和 config

需要准备的材料

  • SVD UNet 代码、FP16 权重分片或等效权重文件。
  • config、tokenizer/condition 配置、文件哈希脚本。

需要进行的最小步骤

  1. 记录代码 commit 和 config 文件哈希。
  2. 记录所有权重文件的 SHA-256。
  3. 检查权重是 FP16 版本，而不是误用 FP32 单文件。
  4. 读取 in_channels、condition 维度、VAE 缩放因子的来源。
  5. 把 config 中的关键字段复制到 model_manifest.json。

需要的分工成员

  • A：确认存储空间和文件完整性。
  • B：核对代码/config 的模型结构。
  • C：准备 Baseline 权重加载记录。
  • D：确认 Treatment 使用同一权重来源。
  • E：独立计算哈希并检查 manifest 完整性。

实验阶段性成功标志

  • 代码、权重和 config 都有哈希。
  • 权重精度与实验声明一致。
  • 关键 shape 字段来自 config，而不是凭猜测填写。
  • Baseline/Treatment 只有目标结构差异。

任务卡 CL5：建立最小 SVD UNet forward

需要准备的材料

  • VideoUNet 入口、权重加载器、固定随机种子。
  • 输入适配脚本、config 读取脚本、最小 forward 日志。

需要进行的最小步骤

  1. 打印实际 VideoUNet.forward() 签名。
  2. 根据 config 构造 x、时间步 t 和 conditioning 输入。
  3. 在 CUDA 上加载 FP16 UNet，执行一次 no_grad/inference_mode forward。
  4. 记录输入形状、参数量、输出形状、dtype 和 device。
  5. 明确本实验不做 VAE decode。

需要的分工成员

  • B：完成模型入口和输入构造。
  • A：确认显存余量和 GPU 运行状态。
  • C：记录 Baseline 最小 forward 证据。
  • D：独立复现一次相同 forward。
  • E：复核 shape、dtype、路径和指令。

实验阶段性成功标志

  • 最小 UNet forward 在 CUDA 上完成。
  • 所有关键输入输出 shape 可解释。
  • C 与 D 两次最小 forward 的输出 shape 一致。
  • 没有把 VAE 或完整采样管线混入实验对象。

任务卡 CL6：核对 latent 空间形状

需要准备的材料

  • VAE downscale 记录、config、L0–L3 输入表。
  • shape 计算表、错误案例日志。

需要进行的最小步骤

  1. 从 config 读取 latent channels 和空间下采样倍率。
  2. 若要测试 512×256 像素，按倍率反算 latent 空间尺寸；倍率为 8 时得到 64×32，而不是无条件使用 32×32。
  3. 将候选 L0–L3 转成内部 latent 尺寸。
  4. 用每个候选尺寸检查模型是否接受。
  5. 把最终 shape 写入配置，不在每次运行中临时计算。

需要的分工成员

  • B：解释 shape 与模型结构关系。
  • C：准备 Baseline 候选配置。
  • D：检查 Treatment 是否兼容同一 shape。
  • A：监控显存和实例状态。
  • E：交叉验证 shape 计算和记录。

实验阶段性成功标志

  • latent 尺寸来自 config 和实际 forward，不来自文档示例。
  • L0–L3 每个候选输入都有可解释的内部 shape。
  • 发现 shape 不匹配时已修正，而不是继续运行错误实验。

任务卡 CL7：执行 L0–L3 显存预检

需要准备的材料

  • L0–L3 配置表、显存统计脚本、独立进程运行脚本。
  • memory_preflight.csv、OOM 错误日志、GPU 状态日志。

需要进行的最小步骤

  1. 从 L0 开始逐级执行一次 forward。
  2. 每轮前重置峰值统计。
  3. 记录 max_memory_allocated()、max_memory_reserved() 和是否 OOM。
  4. 每级独立进程运行，失败后继续下一级。
  5. 找到 Baseline 和 Treatment 共同可运行的候选配置。

需要的分工成员

  • C：执行 Baseline 显存预检。
  • D：执行 Treatment 显存预检并旁证 Baseline。
  • A：检查 GPU 使用率和租户配额。
  • B：确认每级输入到达正确模型入口。
  • E：整理 OOM 记录和共同可运行集合。

实验阶段性成功标志

  • L0–L3 均有“通过/OOM/错误”的明确结果。
  • Baseline 和 Treatment 的候选交集已列出。
  • 峰值显存与运行错误都有原始日志。
  • 没有把不同显存统计口径混在一起。

任务卡 CL8：锁定共同输入级别

需要准备的材料

  • 预检交集、配置模板、运行断言、selected_config.json。

需要进行的最小步骤

  1. 选择 Baseline 与 Treatment 都能运行的最高级别。
  2. 对共同级别连续运行 5 次 forward。
  3. 写入固定输入 shape、batch、帧数、dtype、seed。
  4. 在脚本中加入 BASELINE_LEVEL == TREATMENT_LEVEL 断言。
  5. 将配置文件设为共享只读。

需要的分工成员

  • C：验证 Baseline 连续运行。
  • D：验证 Treatment 连续运行。
  • B：审核输入配置与模型 config。
  • A：检查 GPU 显存和实例容量。
  • E：冻结配置哈希并记录共同级别。

实验阶段性成功标志

  • selected_config.json 唯一且只读。
  • 双方连续 5 次 forward 无 OOM。
  • 输入 shape、dtype、随机种子和 GPU 编号有记录。
  • 后续任何配置变化都需要新 run ID 和新数据目录。

任务卡 CL9：定位 FFN 模块和权重

需要准备的材料

  • named_modules() 输出、Linear/Conv 参数表、模型结构记录。
  • ffn_catalog.json、FFN 前缀审计表。

需要进行的最小步骤

  1. 打印所有 Linear、Conv、attention 相关模块的完整名称和输入输出维度。
  2. 找到 attention 后的连续线性层及其激活。
  3. 排除 to_q、to_k、to_v、to_out 等注意力投影。
  4. 把 FFN 模块完整前缀写入 ffn_catalog.json。
  5. 由第二名成员独立核对模块数量。

需要的分工成员

  • B：主导 FFN 定位和结构解释。
  • C：核对 Baseline 中 FFN 的覆盖范围。
  • D：确认后续替换能在相同名称下工作。
  • A：无需模型判断，负责运行资源。
  • E：独立检查模块名和目录字段。

实验阶段性成功标志

  • FFN 前缀由实际模块树确定。
  • 注意力投影没有被列入 FFN。
  • 模块数量、Linear 维度和参数大小均有记录。
  • ffn_catalog.json 能被另一名成员用于重建模块列表。

任务卡 CL10：计算 FFN 占比并执行决策

需要准备的材料

  • Baseline 分层 FLOPs、FFN 模块清单、占比公式和决策记录。
  • ffn_decision.md。

需要进行的最小步骤

  1. 计算 FFN FLOPs 占整个 UNet 的比例。
  2. 记录分子、分母、统计覆盖范围和计算脚本版本。
  3. 若占比不低于 15%，执行纯 FFN 方案。
  4. 若占比低于 15%，按项目文档在“通道压缩模块”中并入注意投影。
  5. 将最终 RQ 表述和实验标签写入决策记录。

需要的分工成员

  • C：计算 Baseline 占比并提供原始数据。
  • B：确认 FFN 分组没有漏掉结构。
  • D：依据决策准备 Treatment 范围。
  • A：确认测量环境没有改变。
  • E：复算占比并审核是否达到决策阈值。

实验阶段性成功标志

  • FFN 占比和阈值判断可仅凭文件复算。
  • 纯 FFN 或扩展压缩模块的选择已明确。
  • Treatment 的替换范围与决策一致。
  • 报告中不会把“通道压缩模块”误称为纯 FFN。### 任务卡 CL11：建立 hook/profiler 测量口径

需要准备的材料

  • ModuleProfiler、torch.profiler、小型 dry-run 模型。
  • 口径说明、输出 CSV 模板、独立复算脚本。

需要进行的最小步骤

  1. 用 hook 记录模块输入输出、dtype、device、参数量。
  2. 统计整体/FFN/attention/conv 的 FLOPs 和 B_L1。
  3. 用 profiler 做一次交叉检查；若 profiler 不提供 FLOPs，记录而不依赖。
  4. 记录未覆盖算子、einsum、baddbmm 和自定义 attention。
  5. 在 dummy 模型上由两人独立运行，核对结果。

需要的分工成员

  • C：实现并运行 Baseline hook。
  • D：用相同口径独立运行 Treatment dry-run。
  • B：解释非标准算子和模块覆盖。
  • A：保证 dry-run 不发生 OOM 或资源争用。
  • E：复核公式、单位和两人结果是否一致。

实验阶段性成功标志

  • hook 的模块覆盖范围、FLOPs 公式和字节公式已冻结。
  • 两人在 dry-run 中得到可解释的一致结果。
  • 未覆盖算子有比例或明确说明。
  • 后续 Baseline/Treatment 使用同一版脚本。

任务卡 CL12：云端带宽标定

需要准备的材料

  • GPU 大张量复制脚本、CUDA Event、独立进程启动脚本。
  • cloud_bandwidth.csv、GPU 状态日志。

需要进行的最小步骤

  1. 选择 256 MiB、512 MiB、1 GiB 或更大缓冲区，按实际显存调整。
  2. 分配源/目标 GPU 张量并预热 3 次。
  3. 复制重复 5 次，CUDA Event 计时。
  4. 按读源+写目标计算总字节。
  5. 计算可达带宽中位数，并记录最大/最小值。

需要的分工成员

  • A：启动独立实例和固定 GPU 环境。
  • B：确认脚本不涉及模型输入。
  • C：运行带宽基准。
  • D：独立重跑一次主要尺寸。
  • E：复算字节、中位数和单位。

实验阶段性成功标志

  • 至少 3 组有效尺寸，每组至少 5 个计时样本。
  • 选择的主结果已进入平台阶段区间。
  • C/D 结果在约 5% 范围内，或差异有资源/后台负载解释。
  • CSV 可以从原始日志重算。

任务卡 CL13：云端 FP16 GEMM 标定

需要准备的材料

  • FP16 GEMM 基准、CUDA Event、GPU 显存监控。
  • cloud_gemm.csv、实例状态日志。

需要进行的最小步骤

  1. 从 4096³ 或 8192³ 开始测试，按显存逐步增加尺寸。
  2. 预热至少 5 次。
  3. 每个尺寸运行至少 20 次，记录实际总耗时。
  4. 按 2MNKR/t 计算实测吞吐。
  5. 保留未达到饱和区间的尺寸，不强行用其替代主结果。

需要的分工成员

  • A：监控 GPU 显存和实例状态。
  • B：确认 FP16 计算路径和 Torch 设置。
  • C：执行主要 GEMM 标定。
  • D：独立运行一个主尺寸作复测。
  • E：核对 M/N/K、重复次数和 FLOPs 公式。

实验阶段性成功标志

  • 至少一个尺寸进入可解释的饱和区间。
  • 取得 3 组有效吞吐结果。
  • 没有 OOM、MIG 误标称或 CPU fallback。
  • C/D 同尺寸复测结果有记录。

任务卡 CL14：冻结云端屋脊点

需要准备的材料

  • 带宽表、GEMM 表、GPU 官方规格页。
  • cloud_roofline.json、单位换算表。

需要进行的最小步骤

  1. 统一带宽为 Byte/s、算力为 FLOP/s。
  2. 计算 I*=π_measured/β_measured。
  3. 计算标称屋脊点并标注来源。
  4. 记录 GPU 是否 MIG、实例编号和测量日期。
  5. 冻结云端平台参数版本。

需要的分工成员

  • A：确认 GPU 身份和实例限制。
  • B：确认计算没有涉及模型 FLOPs。
  • C：计算实测屋脊点。
  • D：复算标称屋脊点和主口径。
  • E：审核文件结构、单位和来源。

实验阶段性成功标志

  • cloud_roofline.json 同时包含实测和标称参数。
  • 每个参数都有测量尺寸或官方来源。
  • 后续模型实验使用同一冻结版本。

任务卡 CL15：Baseline 结构测量

需要准备的材料

  • selected_config.json、Baseline 模型、冻结 hook。
  • run_cloud_baseline_*.json、原始输出和随机种子。

需要进行的最小步骤

  1. 独立进程加载原尺寸 Baseline。
  2. warmup 2–3 次并丢弃首次正式结果。
  3. 运行 5 次结构测量。
  4. 记录整体/FFN/attention/conv 的 FLOPs 和 B_L1。
  5. 计算各层算术强度并保存每次原始值。

需要的分工成员

  • C：执行 Baseline 全部结构测量。
  • D：在场见证并检查运行配置。
  • A：监控 GPU 和实例状态。
  • B：核对模块 hook 是否命中。
  • E：复核 JSON 字段和可复算性。

实验阶段性成功标志

  • 5 次 Baseline 结构结果齐全。
  • 整体/FFN/attention/conv 均有明确统计。
  • 输出 shape 和 dtype 符合配置。
  • D 对该轮“只属于 Baseline”给出见证记录。

任务卡 CL16：Baseline 时间与显存测量

需要准备的材料

  • 不含 profiler 的计时脚本、独立进程、GPU 显存监控。
  • cloud_time.csv、run_*_time.json。

需要进行的最小步骤

  1. 在独立进程加载 Baseline 并 warmup。
  2. 用 CUDA Event 或同步前后计时测量至少 5 次前向。
  3. 记录中位时间、最小/最大值和峰值显存。
  4. 记录当前 GPU 是否共享、是否存在其他进程。
  5. 与结构测量分开保存，不用 profiler 时间替代正式计时。

需要的分工成员

  • C：执行时间和显存测量。
  • D：独立确认计时脚本没有 profiler。
  • A：检查 GPU 无异常负载。
  • B：确认前向输入和结构未变化。
  • E：计算中位数并记录样本分布。

实验阶段性成功标志

  • 至少 5 次有效前向时间。
  • 中位时间和峰值显存有原始数据。
  • 脚本中没有混入 profiler 开销。
  • 运行前后配置哈希一致。

任务卡 CL17：构造 Treatment

需要准备的材料

  • ffn_catalog.json、FFNBottleneck、Baseline 模块映射备份。
  • treatment_manifest.json、固定 seed。

需要进行的最小步骤

  1. 仅替换 FFN 目标 Linear，瓶颈比例设为 0.5。
  2. 保持输入输出维度不变。
  3. 记录被替换和未替换模块。
  4. 运行一次形状验证 forward。
  5. 计算 Treatment 参数量和模块数量差异。

需要的分工成员

  • D：实施替换。
  • B：审核模型结构与 FFN 范围。
  • C：确认 Baseline 未被改写。
  • A：检查显存是否异常。
  • E：逐项检查替换清单和维度。

实验阶段性成功标志

  • 替换清单完整，输入输出维度一致。
  • attention 投影没有被误替换。
  • Treatment 输出 shape 与 Baseline 一致。
  • Treatment manifest 可重新构造同一模型。

任务卡 CL18：Treatment 结构、时间和复核

需要准备的材料

  • Treatment 模型、同一 hook、同一输入配置和独立日志目录。
  • run_cloud_treatment_*.json、Baseline 复核配置。

需要进行的最小步骤

  1. warmup 后执行 5 次结构测量。
  2. 另起无 profiler 进程执行至少 5 次计时。
  3. 记录整体/FFN/attention/conv 指标和峰值显存。
  4. 由 C 独立复跑一次 Treatment 的主要配置。
  5. 重跑 Baseline 一次，记录时间漂移。

需要的分工成员

  • D：执行 Treatment 主测量。
  • C：进行 Treatment 独立复跑和 Baseline 复核。
  • B：确认未引入非目标结构变化。
  • A：保持 GPU 实例和环境不变。
  • E：接收并复核两套独立输出。

实验阶段性成功标志

  • Treatment 至少 5 次结构和 5 次计时数据。
  • C 的复跑与 D 的主结果可比较。
  • Baseline 时间漂移原则上不超过约 5%。
  • 配置、代码、权重哈希均与门禁时一致。

任务卡 CL19：数据质控与异常处理需要准备的材料

  • Baseline/Treatment 全部 run、数据字典、异常日志。
  • 统计脚本、缺失字段检查表、备份目录。

需要进行的最小步骤

  1. 检查每个 run 的环境、配置、输入、模型变体和指标字段。
  2. 复核 FLOPs、B_L1、算术强度、时间和显存。
  3. 标记离群值并保留原始数据。
  4. 对缺失、重复和单位错误逐项修正记录。
  5. 生成 cloud_analysis_table.csv。

需要的分工成员

  • E：主导数据质控和缺失检查。
  • C：解释 Baseline 异常。
  • D：解释 Treatment 和复跑差异。
  • B：审核模型结构字段。
  • A：审核 GPU 平台字段和测量环境。

实验阶段性成功标志

  • 每个结论字段有 run ID。
  • 所有缺失/离群值都有处理状态。
  • Baseline/Treatment 行数、样本数和配置一一对应。
  • 分析表能从原始文件重新生成。

任务卡 CL20：云端 Roofline 与图件

需要准备的材料

  • 冻结平台参数、cloud_analysis_table.csv、绘图脚本。
  • 云端实测/标称屋脊点和图件模板。

需要进行的最小步骤

  1. 对整体和四个层级计算 I=FLOPs/B_L1。
  2. 计算 q=I/I* 并标注 compute/memory-bound。
  3. 用实测屋脊点画实线，标称值画虚线。
  4. 用箭头连接 Baseline/Treatment。
  5. 保存 CSV、SVG/PNG、图注和生成脚本。

需要的分工成员

  • E：主导数据表和图件生成。
  • B：确认整体/FFN/attention/conv 的统计范围。
  • C：复核 Baseline 点。
  • D：复核 Treatment 点和箭头方向。
  • A：确认实测平台屋脊点。

实验阶段性成功标志

  • 整体和 FFN 点均出现在图上。
  • 实测/标称屋脊点清晰区分。
  • 每个点能追溯到 run ID。
  • 图可以由冻结 CSV 和脚本重新生成。

任务卡 CL21：交接与最终验收

需要准备的材料

  • 云端实验目录、云侧结论、跨平台交接表、README。
  • 关键文件 SHA-256、异常和限制清单。

需要进行的最小步骤

  1. 归档平台、环境、Baseline、Treatment、分析和图件。
  2. 生成《云侧到边缘侧的交接表》，列出方向指标而不混淆绝对值。
  3. 在干净进程重跑最小 forward 和一项平台基准。
  4. 由非主要操作者检查缺少字段、未记录异常和不可复现命令。
  5. 提交 A–E 五人联合验收。

需要的分工成员

  • A：确认平台参数和资源记录完整。
  • B：确认模型代码、权重和 config 可重载。
  • C：确认 Baseline 数据可追溯。
  • D：确认 Treatment 和复核可追溯。
  • E：确认数据包、README 和交接表完整。

实验阶段性成功标志

  • 云端数据包可按 README 完成最小复现。
  • 交接表明确“方向可比较、绝对值不可直接比较”。
  • 所有主结论能定位到 CSV/JSON/图件。
  • 五人均完成签字或等效的在线确认。

3. 云端实验的强制性通过条件

满足以下条件，云端对照组才可以向跨平台组交付：

  1. GPU 型号、显存、CUDA、驱动和 PyTorch 版本明确；
  2. 环境和模型工件有哈希；
  3. SVD UNet 最小 forward 成功，实验范围不含 VAE 解码；
  4. latent shape 来自 config 和实际 forward；
  5. Baseline/Treatment 使用同一输入级别、FP16、同一模型代码口径；
  6. FFN 前缀经过独立复核；
  7. Baseline 至少 5 次结构测量和 5 次时间测量；
  8. Treatment 至少 5 次结构测量和 5 次时间测量；
  9. 至少 1 次 Baseline 复核，漂移有量化说明；
  10. 平台实测和标称屋脊点分开记录；
  11. 原始日志、结构化结果和图件齐全；
  12. 数据包通过 A–E 五人联合验收。

4. 云端组与其他组的交接格式

交接表至少包含：

字段 说明

云端组不向边缘组交接的东西：

  • 不交接“云端性能优于边缘”的绝对值结论；
  • 不交接云端功耗 /J 结论；
  • 不把完整 SVD 生成时间当作 UNet 性能；
  • 不把 MIG 实例标称参数当作全 GPU 参数。

8. 方案结论

云端组的职责是建立一个可复现、可审计的“原尺寸 SVD UNet Baseline 与 FFN Treatment”参照系。最重要的不是追求某个漂亮的墙钟时间，而是保证：

  1. Baseline 和 Treatment 的结构、输入和统计口径严格一致；
  2. 平台参数来自实际云端 GPU；
  3. 所有数据能够回溯和复算；
  4. 向跨平台组交付“方向数据”而不是未经说明的绝对性能比较。

只要 CL0–CL21 全部通过，云端对照组就可以作为项目 v5.0 的合格对照平台，与边缘组的 8 GB 降配实验共同回答 FFN 压缩在不同算力—带宽约束下是否发生方向一致的瓶颈迁移。
