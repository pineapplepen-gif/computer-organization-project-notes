GPU实验方案

本机单平台 SVD FFN Roofline 实验计划

Summary

不再申请云 GPU，直接在本机 NVIDIA GeForce RTX 5060 Laptop GPU 8 GB 上测试 SVD UNet 的 FFN 通道压缩效果。实验正式名称调整为“本机 GPU 平台上的 SVD UNet FFN 压缩与 Roofline 分析”，平台类别固定为 local_rtx5060_laptop。

调整后的研究范围：

  • 回答 RQ1：FFN 压缩后，整体和分层 FLOPs、访存下界、算术强度如何变化。
  • 回答 RQ2：该变化在本机实测算力和带宽约束下推向 compute-bound 还是 memory-bound。
  • 不回答完整 RQ3：没有云 GPU 和 Jetson 配对数据，不能声称得到跨平台一致性结论。
  • 不回答 RQ4：笔记本没有可靠的整板功耗采集，不使用 nvidia-smi 瞬时功耗冒充功耗实验。

目标是在 1–2 个工作日内完成一个可复现的单平台实验包；如果原尺寸模型在 8 GB 显存下无法运行，则按预定降级路径交付结构分析和容量墙证据。

Implementation

1. 环境与平台冻结

在 local_svd_ffn_roofline/ 下建立独立实验目录，不修改现有课程资料。

  • 优先使用本机 Python 3.13、PyTorch 2.15.0+cu132 和已可用的 CUDA 13.2。
  • 通过隔离 venv 加载 PyTorch，避免污染全局 Python。
  • 如果官方 SVD 代码无法兼容当前 Python/Windows，则创建 Python 3.11 + Blackwell 兼容 PyTorch 环境。
  • 固定代码 commit、CUDA、驱动、PyTorch、attention backend、模型权重 SHA-256 和随机种子。
  • 当前 C 盘剩余约 41.5 GB；项目缓存和权重总计控制在 20 GB 内。
  • 权重下载需要 Hugging Face 许可确认、登录和网络授权；令牌不得写入项目或日志。

2. 模型实现与入口门禁

正式实现优先使用 Stability-AI/generative-models 的 VideoUNet 和官方 stabilityai/stable-video-diffusion-img2vid-xt 权重。

  • 只测试 UNet FP16 前向，不运行 VAE 解码、采样器或完整视频生成。
  • 打印实际 forward() 签名，根据 config 和真实 VAE 空间倍率构造 latent 输入。
  • 使用固定 x/t/conditioning、固定 seed 和统一 attention backend。
  • 检查输出 shape、dtype、device、CUDA 可用性和 CPU fallback。
  • 官方实现无法运行时，迁移至 Diffusers 并作为独立实现保存；官方和 Diffusers 数据不得混用。
  • 若两套实现均无法完成最小 forward，停止性能实验，转入平台标定和静态结构分析降级路径。

3. 本机平台标定

在模型测量前完成：

  • 记录 RTX 5060 Laptop 的显存、compute capability、驱动和运行状态。
  • 测试 256、512、1024 MiB GPU 复制带宽，预热 3 次，每个尺寸记录 10 次并取中位数。
  • 测试 2048³、4096³、8192³ FP16 GEMM，预热 5 次，每个尺寸重复 20 次。
  • 计算实测屋脊点 I* = FP16_GEMM_吞吐 / 可达带宽。
  • 同时保存厂商标称参数作为虚线参考，主图只使用本机实测值。
  • 关闭游戏、浏览器硬件加速、录屏和显卡超频；运行前后保存 GPU 状态日志。

4. 输入级别与显存门禁

依次测试：

级别 像素分辨率 帧数 Batch
L0 512×256 14 1
L1 512×256 8 1
L2 384×192 14 1
L3 256×256 8 1
  • 每级使用独立 Python 进程，记录峰值分配、峰值保留、系统内存余量和完整 OOM 文本。
  • 选择 Baseline 与 Treatment 都能连续运行 5 次的最高级别。
  • CPU offload 只允许用于 shape、hook 和结构验证，其运行时间不得进入性能或 Roofline 结论。
  • 如果全部级别 OOM，实验降级为平台标定、模型静态结构分析和容量墙分析。

5. FFN 定位与 Treatment

  • 输出所有 Linear、Conv 和 Attention 模块名称。
  • 排除 to_q/to_k/to_v/to_out，生成经过审计的 ffn_catalog.json。
  • 计算 FFN FLOPs 占总 FLOPs 的比例；低于 15% 时，按课程方案并入注意力投影并修改术语。
  • Treatment 仅在审计通过的 FFN Linear 上应用 r=0.5 瓶颈层：
    h=max(1,int(0.5*d_out))。
  • 不新增激活函数，不改变输入输出维度，不替换注意力投影。
  • 逐层计算参数变化比例。若某层替换后参数或 FLOPs 增加，报告中必须如实标记。

6. Baseline/Treatment 测量

  • 结构测量：用统一 hook 统计整体、FFN、Attention、Conv 的 FLOPs、B_L1 和算术强度。
  • 正式计时：使用独立非 profiler 进程，预热 3 次，执行 10 次前向并保存全部样本。
  • 每个变体至少完成 5 次结构测量和 10 次有效计时样本。
  • 执行 Baseline → Treatment → Baseline 复核。
  • Baseline 复核漂移超过约 5% 时，检查背景负载、显存、时钟和热状态后重跑。
  • 原始 run 只追加、不覆盖；每次运行必须有唯一 run_id 和配置哈希。

7. 分析与报告

对整体、FFN、Attention、Conv 分别计算：

  • I = FLOPs / B_L1
  • q = I / I*
  • compute-bound 或 memory-bound 分类
  • Treatment 相对 Baseline 的 FLOPs、字节和算术强度变化方向

报告明确区分三种证据等级：

  1. GPU 完整前向加有效计时：可用于 RQ1、RQ2。
  2. 降级输入、offload 或结构-only 运行：只用于结构和容量分析。
  3. 仅静态分析：不能声称实测性能结论。

Test Plan and Acceptance

  • CUDA、FP16 GEMM 和最小 UNet forward 必须真实运行，不能静默回退 CPU。
  • 模型 commit、权重、配置和环境必须具有可追溯哈希。
  • Baseline 与 Treatment 必须使用相同输入、精度、seed 和 attention backend。
  • Treatment 必须证明没有替换注意力投影，且输出 shape 与 Baseline 一致。
  • 所有 OOM、降级、offload 和异常运行必须保留原始错误或状态。
  • Roofline 图必须能由冻结 CSV/JSON 和绘图脚本重新生成。
  • 在干净进程中按 README 重跑最小 forward 和一项平台基准。
  • validate_package.py 必须检查字段、哈希、run ID、样本数和平台标签。
  • 只有具备有效 GPU 计时数据的运行才能进入 RQ2 性能结论。
